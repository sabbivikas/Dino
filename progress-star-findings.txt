THE ARC
-------
An owner-only, flag-gated experimental tab. Tap the star -> it is "sent out" ->
a real browser-agent (AGI vendor) searches the live web for ONE gentle, free
thing to do THIS WEEK in Saint Paul, MN -> a cheap model (gpt-4.1-mini) picks
the single best fit and writes dino's "why" in his lowercase, no-dash voice ->
a reveal card offers one of four outcomes (add to calendar / book it / finish
signing up / warm empty-handed). Past findings + the real comfort recs rest on
an isolated shelf below the star. Four star states: idle, sending (glide off +
fade), away ("the star is out looking"), back (glide-in on a result). Reduce
Motion falls back to opacity, following the copied star class.

AGI API — REAL BEHAVIOR (see scratchpad/findings-QA)
----------------------------------------------------
Real browser-agent sandbox, two planes: control plane api.agi.tech/v1 (session
lifecycle) + per-session agent plane (/user_message + SSE /events + /cancel +
/terminate). start_url is mandatory. The 30-step kill is a live THOUGHT-count
kill on the SSE stream (cancel + terminate + DELETE); the session is ALWAYS
deleted in a finally block. Real runs proved the kill fires at exactly the
threshold and leaks zero sessions.

SURPRISE worth the owner's attention: with the first prompt the search agent
explored productively (found the SPPL library + parks pages) but burned all 30
steps chasing exact per-event permalink URLs and never emitted final JSON --
hitting the step cap with 0 candidates. A convergence tweak to buildSearchPrompt
("be decisive, don't chase permalinks, emit JSON as soon as you have a few")
fixed it: runs 2 & 3 returned 6 real candidates in 5-6 steps / ~90-100s. The
Firecrawl fallback was NOT needed -- the API works; it just needed steering.

FIX PASS — CLIENT REACHABILITY (two bugs; server was already correct)
---------------------------------------------------------------------
A real production task (fOBoTl257mhN96RRvEjP) completed on the server — status
found, 8 steps, Hatha Yoga Class / SPPL / add_to_calendar — and the client could
not reach it at all. Two independent causes:

BUG 1 — the push had no door. sendFindingPush sent only notification{title,body};
AppDelegate reads userInfo["deepLink"] then userInfo["action"] and otherwise
falls through to home, and ContentView had no "finding" case. FIX: the push now
carries data { deepLink: "dino://finding/{taskId}", taskId }, and ContentView
gained ONE additive case routing it to tab slot 3 + the task's reveal.

BUG 2 — the tab never asked the server. FindingsTabView opened on a hardcoded
idle star and the local shelf only; getFindingTask REQUIRED a taskId, and the
taskId was never persisted until the ~2 minute call returned — so an app killed
mid-search lost the task permanently and had no way to ask about it. FIX:
getFindingTask's taskId is now OPTIONAL (absent → the caller's most recent task,
orderBy createdAt desc limit 1; no task at all → a quiet {taskId:"",
status:"none"} instead of a not-found throw), the client upserts the moment an
id exists and writes a dino.findings.pendingSince marker when a send BEGINS,
and the tab reconciles with the server on appear + on scenePhase .active
(polling every ~10s while a task is still searching and the tab is visible).

PASS: RAW-REPLY LOG + SOFTENED BOOKABLE BIAS (server-only, no rebuild)
======================================================================
WHY: task oLCcj9OJzWwASFHIIWXp came back outcome=empty with steps=5,
durationMs=105359, preferBookable=TRUE and zero candidates. Not a cap-kill and
not an error, so the agent finished and produced nothing parseable — and we
could not tell "genuinely found nothing" from "replied with prose that parsed
to zero", because the raw reply was never logged. Bias-OFF runs found 6 in 5-6
steps, so the narrowed registration-portal source list was the prime suspect.

1. RAW-REPLY LOGGING. New pure helper summarizeAgentReply(raw, cap) in
   starFindings.ts -> { truncated, looksJson, length }: single-lines the reply
   (so it stays ONE log entry), truncates at AGENT_REPLY_LOG_CAP = 1200, and
   reports the PRE-truncation length plus whether the reply looked like JSON
   ([ or { once ```json fences are stripped, judged exactly as parseCandidates
   sees it). startFindingTask logs "findings_agent_reply" at INFO right after
   parseCandidates, for EVERY run (found and empty) so there is a baseline.
   looksJson is the flag that splits a genuine "[]" from a prose reply. Adds
   ZERO agent steps — it only logs what already came back. No user PII (the
   agent's own text about public listings); the API key / auth headers live in
   agiClient request options and are never in a message body.

2. SOFTENED BOOKABLE BIAS (owner: "I'd rather get candidates with honest
   registration flags than zero candidates"). The preferBookable branch of
   buildSearchPrompt now PREFERS instead of RESTRICTS: registration portals are
   still named FIRST as the preferred starting point, but the agent is told to
   FALL BACK to general gentle listings rather than return nothing, to set
   registrationNeeded HONESTLY per candidate, to prefer (not require) a
   register/sign-up affordance, and that "returning zero candidates when gentle
   free events exist is a failure". The two rules that got runs down to 5-6
   steps are preserved verbatim in the branch: do NOT open each event's detail
   page, and emit the JSON as soon as you have a few candidates. Same step
   budget. The bias-OFF prompt is BYTE-IDENTICAL to HEAD (diffed).

SERVER-ONLY / NO REBUILD: ZERO .swift files in this commit — only
functions/src/{starFindings.ts,index.ts}, two test files and this file. The
client contract is untouched: request stays ["preferBookable": Bool], the
callable response stays { taskId, status, steps, outcome, finding } and the
